WAL-Reset Bug：触发、漏测与旧版本规避

一次 checkpoint 把上一代 WAL 的进度写进了下一代 WAL。结果不是只会 “损坏”：已返回成功的事务也可能永久消失，而 integrity_check 仍然返回 ok。

决策结论：升级或回移官方 salt 校验是首选。无法改 SQLite 时，必须从结构上消除 write 与 checkpoint 的跨连接重叠，或 停写后退出 WAL；仅调 checkpoint 模式、超时和同步级别不够。

真正的触发场景

必须同时具备 WAL、同一数据库文件上的至少两个连接、不同执行线程或 进程，以及 checkpoint 与能够 reset WAL 的 commit 的精确交错。普通 “多线程使用 SQLite”并不足以触发。 

checkpointer A                 writer B                  wal-index
     |                            |                     nBackfill = L
     | read cached header         |                     salt = S
     | mxFrame = L                |
     |                            | reset WAL
     |                            | append m frames      nBackfill = 0
     |                            | commit               salt = S + 1
     | acquire read-lock 0        |
     | stale test: 0 < L          |
     | publish nBackfill = L      |                     nBackfill = L
     |                            | append past frame L
     | later checkpoint skips new frames 1..L
     v
acknowledged write is absent from the database file
  1. 先完成一次 checkpoint，使旧 WAL 可被 reset。
  2. 第二个 checkpoint 缓存旧 mxFrame=L。
  3. 另一连接在 read-lock 0 之前 reset WAL、更新 salt 并提交新 frame。
  4. 旧 checkpoint 误把 nBackfill 写成旧值 L。
  5. 第三次 checkpoint 跳过本代 WAL 的前 L 个 frame。
PASSIVE checkpoint 有 checkpoint lock，但没有 writer lock。问题不是 两个 checkpoint 同时执行，而是 checkpoint 与 writer reset 同时执行。

修复：锁后重验 WAL 代际

修复在 read-lock 0 已取得后比较实时 wal-index salt 与之前缓存的 header salt。发现 WAL 已换代，就不执行旧 backfill，也不发布旧 nBackfill。 

WalIndexHdr *pLive = (WalIndexHdr*)walIndexHdr(pWal);int bChg = memcmp(pLive->aSalt, pWal->hdr.aSalt,                  sizeof(pWal->hdr.aSalt));if( 0==bChg ){  /* backfill and publish nBackfill */}

比较如果发生在早期 header read 之后、加锁之前，writer 仍可在比较后 reset，因此检查位置与检查本身同等重要。

为什么官方测试没有及时覆盖

SQLite 的 100% branch coverage、并发压力测试和 crash testing 都是 真实能力，但 coverage unit 是控制流分支，不是所有跨连接调度序列。

缺口 具体原因 后来如何补上
调度状态空间 五阶段交错横跨多连接，执行每条分支不等于执行该顺序。 新增 fault point 660，在 checkpoint 内精确插入第二连接写入。
自然窗口极窄 官方修复时仍无法在实验室自然复现。 后续自然复现器用大 mmap 的 munmap 延长窗口。
错误延迟显现 第二次 checkpoint 污染进度，第三次才跳过 frame。 回归测试固定完整的跨 checkpoint 状态序列。
oracle 不完整 整笔事务消失后，B-tree 仍可能结构自洽。 同时检查 acknowledged-write counter 与数据库行数。
生产放大器 常见自动 checkpoint 远少于主动、高频 checkpoint。 Tailscale 的规模与操作模式积累了足够事件证据。
16 年延迟主要发生在发现和复现阶段。根因于 2026-03-03 定位后， 3.51.3 于 2026-03-13 发布；不能概括为上游在已知根因后长期不修。

已有场景无法升级：决策顺序

1. 能重编：回移官方补丁

这是最接近升级的低扰动方案。优先使用官方 3.44.6 或 3.50.7 backport；其他 vendor 版本应移植 salt revalidation 与 forced regression test，并在实际加载的连接上核对 sqlite_source_id()。

2. 必须保留 WAL：一个全局 write/checkpoint owner

所有 write transaction 与 checkpoint 必须通过同一个数据库级 gate。只读连接可以保留，但应设为 query_only。多进程 必须用 IPC owner 或所有参与者共同遵守的跨进程锁。 

all writes --------+
                   +---> one owner/gate ---> SQLite writer
all checkpoints ---+

read-only connections --------------------> SQLite readers
PRAGMA wal_autocheckpoint=0;PRAGMA query_only=ON; -- every reader

owner 在停接、排空 writer 后执行 checkpoint。必须监控 WAL 大小、 磁盘余量和读延迟，不能以“永不 checkpoint”作为长期方案。

3. 可以牺牲 WAL 并发：切回 rollback journal

在维护窗口停掉所有连接和写流量，备份并验证后 checkpoint，再切换 模式。必须检查 pragma 返回值；已损坏数据库不能靠切模式修复。 

PRAGMA wal_checkpoint(TRUNCATE);PRAGMA journal_mode=DELETE;
只有当全部写入口、checkpoint 入口和实际 SQLite 副本都被盘点并受控， “全局串行化”才是规避。单进程、单 ORM、SQLITE_THREADSAFE=1 都不能替代这项证明。

检测与恢复闭环

  1. 从每个真实连接查询 sqlite_version() 与 sqlite_source_id()，不要相信 CLI 或 lockfile。
  2. 在 SQLite 外保留单调 transaction ID 或可重放操作日志，检测 ACK 后不可见。
  3. 使用 Online Backup API、VACUUM INTO 或一致性工具；备份后重新打开验证。
  4. 同时检查结构完整性与业务不变量、计数、transaction watermark。
  5. 告警时立即停写并保留同一时刻的 .db、-wal、-shm 和日志。
备份解决恢复，外部 transaction ledger 解决“完整性正常但数据已丢”的 可见性。两者都不能替代预防性补丁或结构性规避。

证据边界

FIL-C 运行了旧版 SQLite 与 serialized demo 路径，完成 6 次提交且 无内存安全或未定义行为报告。原生复现在 Apple M5 Pro/macOS 与 AMD EPYC 7Y83/Linux 上执行。FIL-C 时序不是性能证据；本报告也不把 400 轮无故障外推为概率证明。

本研究未穷举所有历史 SQLite 版本、VFS、文件系统和语言绑定。生产 判定必须以实际连接的 source ID、连接拓扑和 checkpoint 所有权为准。

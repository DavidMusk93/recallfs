Subject
Verus automated program verifier for Rust

一句话结论

Verus 不是“更严格的 Rust 编译器”，而是一套建立在 Rust 语法、所有权系统和 SMT 求解器之上的程序验证器。你先写出函数对所有输入都必须满足的数学契约， 再由 Verus 检查可执行 Rust 实现是否真的满足它。

它填补的是哪一层空白

Rust 能阻止悬垂引用、违反借用规则的数据竞争等问题，但它不会证明二分查找返回的一定是目标， 也不会证明磁盘 extent 的尾位置不会越过容量。测试只能覆盖被执行的样本。Verus 把后一类要求写成逻辑公式，并尝试对所有满足前置条件的输入证明它们。

核心模型：Hoare triple 落进 Rust 源码

如果用 C/系统程序员熟悉的形式看，一个 Verus 函数就是 {P} C {Q}：requires 是调用者必须建立的 P，函数体是可执行代码 C，ensures 是实现必须保证的 Q。 

fn extent_end(start_block: u64, block_count: u64, capacity: u64)
    -> (end: u64)
    requires
        start_block <= capacity,
        block_count <= capacity - start_block,
    ensures
        end == start_block + block_count,
        start_block <= end <= capacity,
{
    start_block + block_count
}

这里的价值不在于“加法很难”，而在于契约同时固定了三件事：加法不溢出、返回值语义正确、 返回范围不越过容量。之后每个调用点都必须证明前置条件成立。

exec

真正编译运行的 Rust。默认模式，保留系统代码的低级控制能力。

spec

描述数学对象和目标性质。纯函数、必须终止，编译时擦除。

proof

给 SMT 求解器的高层证明步骤。受借用与线性约束，编译时擦除。

它为什么特别适合系统代码

普通 SMT 验证的痛点

可变内存、别名、指针和并发资源会迅速放大验证条件。若所有权关系也完全交给求解器， 证明会更重、更脆弱。

Verus 的关键取舍

借用检查器先解决大量内存与别名问题；线性 ghost permission 在证明层表达“谁有权访问哪个资源”。SMT 主要处理剩余的函数性质和状态关系。

因此它的上限不只是纯算法。官方项目已经覆盖 parser/serializer、X.509 验证、持久内存日志、页表、微内核、Kubernetes controller、并发内存分配器等系统场景。 Amazon 文章强调的 unsafe 与自定义锁验证，正是这个组合的目标区间。

最重要的边界：证明只和规格一样可靠

demo 第 3 步故意写了一个弱规格：只要求结果不超过容量。于是永远返回 0 的实现被成功“证明”。Verus 没有犯错，它精确证明了一个没有表达业务语义的命题。

必须审查的可信边界： 顶层规格、assume/admit、外部函数体和库模型、 Verus 与 Z3、Rust/LLVM 编译链、硬件和运行时假设。形式化验证缩小了信任面， 但不会让信任消失。

什么时候值得投入

场景 判断 原因
存储格式、日志恢复、页表、分配器 高价值 状态不变量稳定，错误代价高，核心可切成较小验证边界。
自定义并发原语、原子状态机 高价值但昂贵 线性 ghost state 很匹配，但证明设计本身是专业工作。
纯算法、parser/serializer 良好切入点 输入输出关系清楚，规格相对容易评审。
普通 CRUD、UI、快速变化的胶水代码 通常不划算 规格维护成本高于风险收益，测试与类型系统更经济。
一次验证整个现有 Rust 生态 不现实 Verus 只支持 Rust 子集，依赖和外部行为需要模型或可信边界。

最终判断

Verus 的真正价值不是替代测试，而是把最昂贵的正确性要求变成可由机器反复检查的接口。 对数据库内核而言，最合理的采用方式是从小而稳定的核心开始：页号算术、磁盘格式、 redo/undo 状态机、crash consistency 不变量或自定义并发原语。先让人审查规格， 再让 Verus 审查实现和调用点。

这是一种“把设计意图编译进 CI”的能力。它的收益与 bug 代价、规格稳定性和可信边界大小成正比， 与代码变化频率和外部依赖复杂度成反比。

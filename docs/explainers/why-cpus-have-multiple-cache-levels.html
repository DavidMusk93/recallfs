多级 CPU Cache 为什么有效

Date
2026-09-07
Input shape
concept
Subject
从局部性、AMAT、I/O 复杂度和物理实现理解多级 CPU cache，并用 C 验证

多级 cache 不是把一块大 SRAM 随意切成几段，而是在互相冲突的目标之间做分层： 离执行单元越近，越强调低延迟、端口和带宽；越远，越强调容量、密度、共享和 DRAM 流量过滤。程序的时间与空间局部性，恰好让这种分工成立。

0. 结论先行

多级 cache 的核心收益：用少量、昂贵但极快的存储服务高频访问， 再用逐级更大、更慢、更节能的存储捕获更长的复用距离；同时让私有层隔离每个核心 的高频流量，让共享层承担容量、通信和一致性职责。

它成立需要三个条件：

  1. 访问分布有偏斜，即近期用过或地址相邻的数据更可能再次使用。
  2. 小 cache 的 hit time 明显低于大 cache，且 miss 足够少。
  3. 下一级抓住的 miss 足够多，收益超过多一次 tag lookup、传输和管理成本。

因此，问题不能表述成“为什么不把 32 KiB、256 KiB、数 MiB 相加成一个 L1”。容量相加忽略了访问延迟、布线距离、端口数、并发带宽、功耗和共享协调； 这些才是 L1 不能任意做大的原因。

1. 原文真正解释了什么

Fabian Giesen 的文章用办公桌、文件柜、地下档案室和异地仓库作类比。它最有价值 的不是类比本身，而是把 cache 看成一个物理物流系统：数据要占面积，要穿过实际 导线，要进入端口和队列，还要与其他核心协调。

层次 首要目标 付出的代价
L1I / L1D 最低 load-to-use 延迟；每周期承接大量取指、load、store 容量小、单位 bit 面积和功耗高、通常每核私有
L2 捕获 L1 miss；以 cache line 为主组织传输；缓冲核心与互连 比 L1 慢，但容量更大；拓扑可能私有或由若干核心共享
LLC 减少 DRAM 请求；提供跨核心共享、探测或目录相关能力 访问更远、竞争更多、命中延迟更高且不完全一致
DRAM 提供大容量 首字节延迟高；带宽、bank、队列和 NUMA 都会影响结果

L1I 与 L1D 分开也不是简单地“多放一份缓存”。取指和数据访问发生在流水线的 不同位置，读写语义、访问流、端口需求也不同。拆分后，前端取指与 load/store 可以并行，且各自不必为另一类流量的峰值做同一套折中。

原文采用了 2016 年桌面 x86 常见的“私有 L1/L2、共享 L3、ring bus”图景。 这是有用模型，不是 ISA 保证。现代 x86、Arm、Apple Silicon、chiplet 和 多 socket 系统的层级、共享范围、互连与包含策略都可能不同。

2. 为什么一个大 cache 不能等价替代

2.1 容量与 hit time 互相冲突

cache lookup 至少涉及地址译码、set 选择、tag 读取与比较、way 选择、数据阵列 读取和结果路由。阵列扩大后，word line、bit line、decoder、bank 间连线和输出 mux 都可能变长或变深。分 bank 能缓解问题，但又引入 bank 选择、冲突与布线。 CACTI 这类架构模型之所以同时优化 timing、power、area 和 bandwidth，正说明 “更大而同样快”不是免费的设计点。

2.2 私有带宽与全局共享互相冲突

每个核心的私有 L1 可以并行服务请求。若所有核心每次 load、store 和取指都进入 一个共享大 cache，就必须为总端口数、仲裁、队列、布线和一致性流量买单。共享 cache 的容量可能更有效，但它天然是竞争域；私有 cache 浪费一些重复副本，却 换来低协调成本和随核心数增长的聚合带宽。

2.3 不同层服务不同粒度和职责

核心执行的是字节、word、向量 load/store，层间通常搬运 cache line。靠近核心 的层要支持细粒度访问、store forwarding 和高端口压力；较远层可以把更多面积 用在容量和 line 传输上。更远层还可能承担 coherence filter、directory、 victim 容量或内存侧请求合并。把这些职责塞进一层，不会消除职责，只会把它们 放进每次最热访问的关键路径。

希望得到 物理上倾向于 层次化如何处理
更低 hit latency 更小阵列、更短线、更近放置 小 L1 靠近执行单元
更大容量 更多 bank、更长路径、更高密度 cell L2/LLC 接住较长复用距离
更高并发带宽 复制、分区、更多端口 每核私有层过滤大部分流量
跨核共享 全局互连与一致性协调 只让过滤后的请求进入共享层
更低能耗 少切换电容、短距离传输 高频访问停在最小可用层

3. 可计算的理论支持

3.1 AMAT：逐级 miss 的条件概率

Average Memory Access Time 把层次的收益写成递归期望值。对三级 cache， 若 m1 是 L1 miss rate，m2 是“已经 miss L1 的请求中又 miss L2”的条件 miss rate，则：

AMAT = t1 + m1 * (t2 + m2 * (t3 + m3 * t_mem))

注意 m2 不是所有内存访问中的比例。到达 DRAM 的全局比例是 m1 * m2 * m3。配套 C 程序用一组纯示意参数计算： 

static double
hierarchy_amat(const struct cache_level *levels,
               size_t level_count,
               double memory_cycles)
{
    double tail = memory_cycles;

    while (level_count > 0) {
        level_count--;
        tail = levels[level_count].hit_cycles
             + levels[level_count].conditional_miss_rate * tail;
    }
    return tail;
}
路径 输入 模型结果
L1 → DRAM t1=1, m1=5%, t_mem=200 11.00 cycles/access
L1 → L2 → L3 → DRAM t2=4, m2=20%, t3=20, m3=20% 1.80 cycles/access

加一级 cache 并非必然有利。把“直接付出慢层代价 T”改为 “先查新层 t，以条件概率 m 再访问慢层”，简化 break-even 条件是：

t + m * T < T   =>   m < 1 - t / T

下一级越慢，新层越容易回本；新层自身越慢，它必须截住越多请求。真实处理器还会 并行查 tag、提前发请求、合并 miss，并用乱序执行隐藏部分延迟，因此 AMAT 是 理解方向的期望模型，不是周期精确模拟器。

3.2 局部性、working set 与 reuse distance

Denning 的 locality principle 指出，程序会在一段时间内集中使用有限集合。 时间局部性解释“刚用过的数据值得保留”，空间局部性解释“搬一个 line 而非一个 byte”。working set 不是固定常数：函数切换、阶段切换、请求类型和并发度都会 改变它。

Mattson 等人的 stack distance 给出更直接的 cache 视角：两次访问同一 line 之间出现了多少个不同 line。对理想 fully associative LRU cache，若 reuse distance 为 D、容量为 C 个 line，则 D < C 时命中；miss-ratio curve M(C) = P(D >= C) 描述容量增加如何降低 miss。

多级 cache 等于在这条曲线上选多个工作点：L1 捕获最短 reuse distance，L2 捕获中等距离，LLC 捕获更长距离。若曲线有明显“膝点”，少量高速容量就能挡住 大部分请求；若访问几乎无复用，层次无法凭空创造 locality。

3.3 I/O 复杂度：算术次数不等于数据移动次数

外存模型把快存储容量记为 M，搬运块大小记为 B， 算法成本按块传输次数计算。顺序扫描 N 个连续元素约需 O(N/B) 次传输，而散乱访问可能接近每次访问一次传输。 Hong-Kung 的 red-blue pebble 模型进一步证明：对矩阵乘、FFT 等计算， 数据移动存在独立于算术操作数的下界；只优化指令数不能越过它。

Frigo、Leiserson、Prokop 和 Ramachandran 的 ideal-cache 模型给出一个更强 的连接：某些递归 cache-oblivious 算法在不知道 M 和 B 时，仍能在多级层次上达到渐近最优的数据移动量。它支持的不是 “所有递归代码都快”，而是：若分治不断产生能装入不同层级的小子问题，同一种 访问结构可以同时利用多个 cache level。

3.4 功耗与排队也是一等成本

动态能耗近似随切换电容和电压平方增长；更大的阵列、更长的线和更远的数据搬运 往往切换更多电容。另一方面，共享层和 DRAM 是有限服务率的队列。即使单次延迟 不变，请求率逼近带宽上限时，排队时间也会急剧上升。私有 L1/L2 的过滤既降低 平均延迟，也降低共享互连和内存控制器的到达率。

4.1 随机依赖加载：为什么要让 load 彼此依赖

普通数组扫描可被硬件预取器提前搬运，也允许多个 cache miss 同时在途。随机 pointer chase 让下一地址依赖上一次 load 的结果，压低 memory-level parallelism，更接近测量逐级 load latency： 

uint32_t current = 0;

/* nodes form one shuffled cycle; every load reveals the next address. */
for (size_t step = 0; step < steps; step++)
    current = nodes[current].next;

本次 FIL-C 运行的部分输出：

working-set KiB | ns/dependent-load
              32 |              1.40
             256 |              3.47
            2048 |              8.90
            8192 |             13.29
           16384 |             60.80
           65536 |            117.94
这些台阶说明 working set 会改变访问代价，但不能直接据此宣布“某一级 cache 就是某个大小”。本次程序运行在 FIL-C 0.684 的 Linux/ARM64 VM 中，包含安全 检查、虚拟化、调度、TLB 和预取等影响。cache 容量应从目标机器拓扑读取，延迟 应在目标部署环境重复测量。

4.2 C 是 row-major：交换循环顺序就改变流量

/* contiguous: matrix[row][0], matrix[row][1], ... */
for (size_t row = 0; row < side; row++)
    for (size_t column = 0; column < side; column++)
        sum += matrix[row * side + column];

/* strided: each access jumps side * sizeof(uint64_t) bytes. */
for (size_t column = 0; column < side; column++)
    for (size_t row = 0; row < side; row++)
        sum += matrix[row * side + column];

两段代码执行相同数量的 C 加法，结果也完全相同；但第二段在 side=2048 时每次跨 16 KiB，几乎无法消费刚搬入 line 的相邻 元素。本次 32 MiB 矩阵实验中，最佳观测为： row=1.491 ms、column=12.160 ms， 后者约慢 8.16x。差异同时包含 cache line 利用率、TLB、 预取和编译器向量化效果，不能只归因于某一级 miss。

5. 实际编码技巧

5.1 先改变访问流，不要先猜硬件常数

  • 把热循环的数据放进连续数组，避免 allocator 随机散布的链表和对象图。
  • 缩小 hot record；把低频字段拆到 cold storage，减少每个 line 的无效字节。
  • 只读少数字段时考虑 SoA；经常整条处理时 AoS 可能更好；混合场景考虑 AoSoA。
  • 用 32-bit index 代替 64-bit pointer 前，先确认容量、失效值和重定位语义。
  • 批处理可以提高局部性，但会增加排队延迟；batch size 必须由 SLO 约束。
/* AoS: updating x also fetches cold metadata. */
struct particle {
    float x, y, z;
    uint64_t id, timestamp;
    char label[32];
};

/* SoA: a position-only pass streams only the required fields. */
struct particles {
    float *x;
    float *y;
    float *z;
};

5.2 Blocking：让正在复用的 tile 留在快层

tiling 的目标不是“循环更复杂”，而是把 reuse distance 从整张矩阵缩短到一个 tile。下面是 blocked transpose 的骨架；tile 不是永恒常数，要让 并发活跃的输入、输出和临时数据共同落入预算层，并为 associativity、其他线程 和运行时数据留余量。 

static size_t min_size(size_t a, size_t b)
{
    return a < b ? a : b;
}

void transpose_blocked(double *restrict dst,
                       const double *restrict src,
                       size_t n,
                       size_t tile)
{
    for (size_t ii = 0; ii < n; ii += tile)
        for (size_t jj = 0; jj < n; jj += tile)
            for (size_t i = ii; i < min_size(ii + tile, n); i++)
                for (size_t j = jj; j < min_size(jj + tile, n); j++)
                    dst[j * n + i] = src[i * n + j];
}

5.3 并发写入要按 coherence line 思考

两个线程修改不同变量，若变量落在同一 coherence line，仍会让 line 在核心间 反复失效，这就是 false sharing。C11 的 _Alignas 可以控制起点， 但真正需要的是字段间距至少覆盖目标机器的 line size： 

struct worker_counter {
    _Alignas(128) _Atomic uint64_t value;
    unsigned char padding[128 - sizeof(_Atomic uint64_t)];
};

128 只是示例，不应复制为跨平台真理。对本机读取 line size， 再检查数组 stride 和实际字段 offset。padding 会增大 footprint，可能把问题 从 coherence 转成 capacity/TLB miss，所以只对有证据的热点使用。

5.4 Prefetch 是延迟隐藏，不是减少数据量

顺序和固定 stride 通常先交给硬件预取器。软件 prefetch 只有在地址能提前计算、 中间有足够计算可覆盖延迟、prefetch 不会过早被逐出且不会挤掉热数据时才可能 有益。它仍消耗 request queue、cache 容量和带宽；错误 prefetch 会更慢。 

#if defined(__clang__) || defined(__GNUC__)
#define PREFETCH_READ(ptr) __builtin_prefetch((ptr), 0, 1)
#else
#define PREFETCH_READ(ptr) ((void)0)
#endif

for (size_t i = 0; i < count; i++) {
    if (i + distance < count)
        PREFETCH_READ(&items[i + distance]);
    consume(items[i]);
}

5.5 Streaming 写与 cache pollution

对巨大、单次写入且短期不读回的输出，write-allocate 可能先读入 line，再写满并 驱逐，污染 cache。特定 ISA 的 non-temporal store 可绕开部分层级或降低污染， 但它不是 ISO C，通常有对齐、写合并、可见性和 fence 约束。先证明输出确实超过 cache、短期无复用且带宽受限，再选择目标架构实现；不要把它包装成默认 store。

5.6 代码布局和数据布局是两条流

L1I 与 L1D 分离意味着 instruction footprint 也需要治理。过度模板化、复制 热路径、巨大 switch 和冷错误处理内联会挤压 I-cache；数据端则关注 record stride、pointer chasing 和写共享。二者都慢时不能只看总 cache-misses， 应区分 instruction fetch、data load、TLB 和 LLC 事件。

6. 正确的测量流程

  1. 固定 workload
    真实数据分布、并发度、CPU 亲和性、输入规模和 warm-up。
  2. 读取拓扑
    确认 level、type、size、line size、共享 CPU 和 NUMA。
  3. 定位 stall
    先看 wall time、cycles、instructions、IPC，再下钻 PMU。
  4. 单变量实验
    只改布局、tile 或线程放置之一，重复运行并看尾延迟。

6.1 Linux

# Topology; do not assume L2/L3 sharing.
lscpu -C
find /sys/devices/system/cpu/cpu0/cache -maxdepth 2 -type f -print

# Discover the exact events supported by this PMU first.
perf list cache
perf stat -r 10 -e cycles,instructions,cache-references,cache-misses \
  -- ./workload

# For false sharing on supported systems.
perf c2c record -- ./workload
perf c2c report

通用事件名不保证在不同 CPU 上映射到同一层或同一语义。PMU 事件可能不支持、 被 hypervisor 隐藏，或因计数器不足发生 multiplex scaling。必须结合 perf list、处理器事件文档和采样覆盖率解释。

6.2 macOS / Apple Silicon

# Heterogeneous cores may report per-performance-level values.
sysctl hw.cachelinesize
sysctl hw.l1icachesize
sysctl hw.l1dcachesize
sysctl hw.l2cachesize
sysctl -a | grep 'hw.perflevel'

使用 Instruments 的 CPU Counters 做硬件事件分析，并先配置要采集的 counters。 Apple Silicon 可能有多类核心，每类核心的 L1/L2 大小和共享范围不同；线程迁移 会把多种硬件行为混在一次测量中，因此需要固定场景并检查调度位置。

6.3 不要只看 miss rate

至少同时回答：

  • 每条指令多少 miss，而不是只有“cache references 中的百分比”？
  • miss 是否落到 DRAM，还是被下一层命中？
  • 延迟是否被独立计算或其他并发 miss 隐藏？
  • 瓶颈是 latency、bandwidth、coherence、TLB，还是执行端口？
  • 平均吞吐改善时，p99 是否因共享层排队或 NUMA 访问恶化？

7. 常见误区

误区 边界
更大的 cache 一定更好 理想 stack cache 的 miss rate 随容量不增，但真实 cache 还受 hit time、set conflict、功耗和共享竞争影响。
对齐到 cache line 就会更快 alignment 只控制起点；它不缩小 working set，也不自动消除 conflict、false sharing 或无效字段。
prefetch 能修复随机访问 真正依赖链的下一地址不可提前知道；prefetch 对不可预测 pointer chasing 通常无能为力。
低 miss rate 表示 cache 没问题 少量高代价 miss、HITM、TLB walk 或带宽饱和仍可能主导时间。
编译器会自动修复布局 编译器能重排局部指令，却通常不能改变公开数据结构、指针语义和跨函数 ownership。
coherence 等于 memory consistency coherence 管同一位置的副本；语言内存模型和同步决定跨位置操作的可见顺序。
一次微基准能识别所有 cache level 预取、TLB、DVFS、迁核、虚拟化、插桩和替换策略都会改变曲线，需要多证据交叉验证。

8. 可执行的优化顺序

  1. 先证明 memory-bound。 用 wall time、IPC、stall 和带宽排除计算、锁和 I/O。
  2. 画出访问流。 标明每轮读取字段、stride、复用距离、写入者和共享线程。
  3. 缩小热 working set。 连续化、hot/cold split、压缩 index、去掉多余对象和 indirection。
  4. 缩短复用距离。 loop interchange、blocking、fusion 或按 key/partition 分组。
  5. 治理共享写。 分片计数器、thread-local accumulation、批量合并，再处理 false sharing。
  6. 最后才提示硬件。 软件 prefetch、non-temporal access、huge page 和 NUMA policy 都需要目标机证据。
  7. 验证完整系统。 比较吞吐、p50/p99、CPU、内存带宽、cache/TLB/coherence 事件和内存占用。
最有用的代码评审问题不是“这个对象能不能放进 L2”，而是： 一次业务操作会触碰多少个不同 cache line，这些 line 多久后复用， 又有多少核心会写它们？
